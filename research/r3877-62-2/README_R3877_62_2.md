# R3877.62.2 — Candidate-first Mac recovery evidence triage

**For research and educational purposes only. Physical Kindle hold: `NOT_BOOTABLE`.** No Kindle access, Docker, network, QEMU, SSH, firmware write, boot, recovery attempt, archive extraction, file hashing or candidate content reads.

## Why this exists

The user's actual R3877.62.1 Mac inventory returned `HOLD` / exit 2, examined 12,000 files and exhausted its *regular file* budget. It reported 54 `backup_archive_candidate` files (70,804,845 bytes total) and 5 recovery-document candidates (11,828 bytes). Its broad archive regex includes **any file with `pw3` in its filename**; therefore PW3-OS research ZIP packages may be counted as alleged backup candidates. No partition image was identified in the truncated portion. Nothing was authenticated.

## Narrow improvement

- Reuses the exact prior R3877.62.1 `check_root()` path and symlink protection, pinned by the script SHA256 `996590a6d9271029102cd62be54975bcb10e24d8b4e386e00f687eb12688cc02`, the variant already tested on macOS and Ubuntu GitHub Actions.
- Uses bounded directory-entry and candidate-count limits *separately*; encountering thousands of noncandidate regular files does not prematurely exhaust a candidate quota. Does not follow symlinks; skips hidden and known generated directories (same exclusion policy as R62.1).
- Splits **research-named archive candidates** (e.g. `pw3-r3877-*.zip`, `pw3-os-r*.zip`) from **nonresearch-named backup archives**. This is a filename pattern, not a finding of authenticity: neither group proves a Kindle backup.
- Identifies separate stock partition-image filename candidates (`mmcblk...`, `original_rootfs.img`, etc.), other image/dump filenames, official update package filenames (not equivalent to an independently restorable backup), recovery document filenames and checksum sidecar filenames.
- Reports aggregate counts, sizes and size bands only. **No raw names, paths, hashes or candidate file contents** enter the JSON. No local file writes by the program (your shell may write its JSON via `tee`).
- Reports `bounded_scope_scan_complete` **only for the requested max depth and scanned entries**, not the entire disk. A full count cannot establish recovery authenticity. Unreadable entries and either exhausted budget keep this false.
- Always returns `HOLD` / exit 2, even with stock-image-named files. `NOT_BOOTABLE` is never lifted.

## What to do with results

If all 54 prior archive candidates resolve to research-named packages and there are no credible stock-image candidates within the completed scan, then **the local backup requirement is not satisfied**. Do not infer a recovery route from generic ZIPs or documents. A real recovery gate requires independently identified stock files with known-good hashes/provenance plus an independent, tested recovery interface and a specific failure-mode procedure. That remains separate from the already passed off-device QEMU tests and the still unverified Kindle vendor kernel and application secure-entropy behavior.
