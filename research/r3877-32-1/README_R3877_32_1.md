## Why this audit exists

The user's R3877.32 completed with `PASS_HASH_PINNED_BUILDLOG_COMMAND_SHAPES_ONLY`, but the single likely linker command at line **1666** was `unparsed_shell_quoting`. This is a limitation of the previous `shlex.split` pass, not evidence that the historical musl build failed.

This diagnostic first verifies the entire 1,644,394-byte public log against SHA-256 `a8405a50c1849aebc0fefadcab4e4f7fa7da27d9c1296fa2ce46b73df56ca2ce`, then recomputes the earlier command counts and independently verifies the exact sanitized line-1666 SHA-256 `1082a4442e1edcdcdedcda614abceae9d08961b69bd7bb0c09c2010dbefe6dcd`. It uses a bounded, **nonexecuting** lexical scan to recover a complete-token prefix before the first unmatched quote, if any. It also reports allowlisted textual flags separately when those values cannot be established as complete shell tokens.

The JSON omits complete commands, source/object paths, macro values, variable values and unallowlisted arguments. All tests use synthetic data, **not the real 1.64 MB log**. A `PASS` means bounded, pinned log metadata was classified, not that linker invocation provenance, historical compiler versions, source-to-binary equivalence, Kindle syscall compatibility or recovery are verified.

- `lexical_result` identifies whether quote-aware tokenization completed or stopped; it does **not** establish whether a complex shell command would execute successfully.
- `prefix_driver_class` and `allowlisted_prefix_flags` describe fully parsed prefix tokens only.
- `allowlisted_textual_flags_unverified_as_tokens` lists bounded flags observed in text, without attributing them to parsed arguments or actual execution.
- `historical_builder_linker_binary_and_version_verified`, `source_to_binary_reproducibility_verified`, and other provenance fields remain `false`.
